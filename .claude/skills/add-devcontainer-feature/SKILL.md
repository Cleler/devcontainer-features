description: Scaffold a new Dev Container Feature (or a copy of an official one with Alpine support) — manifest, install.sh, NOTES, tests, CI wiring — following this repo's conventions
---

Add a new Dev Container Feature to `Cleler/devcontainer-features`, end to end. Ask the user for the feature's name and
purpose first if it wasn't already specified (kebab-case id, e.g. `foo-dev`), and whether it is **new** or a **copy of an
official feature** that needs Alpine (apk) support (like `node` and `claude-code`).

Read `AGENTS.md` first: it has the rules of the repository (structure, tests, versions, CI). This skill is the
step-by-step version.

## 1. Before creating anything

- `ls src/` for the current list of features (don't hardcode it, it drifts) and read the features table of `AGENTS.md`.
- Check whether an official or community feature already does this (`ghcr.io/devcontainers/features/*`,
  `ghcr.io/devcontainers-extra/features/*`, `ghcr.io/anthropics/devcontainer-features/*`). If it covers the whole need
  **and works on the distributions we target (Alpine included)**, depend on it instead of reimplementing it.
- If it doesn't work on Alpine only because of the package manager, **copy it and add Alpine** (see "Copy of an
  official feature" below) rather than writing another one.
- A `dependsOn` is resolved from the **published** registry, never from `src/`: if the new feature depends on another
  feature of this repository that isn't released yet, release that one first, in its own PR.

## 2. Files to create

```text
src/<name>/devcontainer-feature.json
src/<name>/install.sh
src/<name>/NOTES.md          # the hand-written documentation; README.md is generated from it
test/<name>/test.sh
test/<name>/scenarios.json   # optional, with one <scenario>.sh per entry
```

### `devcontainer-feature.json`

- **Plain JSON, no `//` comments** (`devcontainers/action` parses it with `JSON.parse`).
- Keys in this order: `name`, `id`, `version`, `description`, `documentationURL`, `licenseURL`, `options`, then the rest
  (`dependsOn`, `mounts`, `containerEnv`, `customizations`...).
- `"version": "1.0.0"` for a new feature. **Never bump a version afterwards for an ordinary change**: the maintenance
  workflow increments the patch version by itself (see `AGENTS.md`). Only a minor/major bump is yours to write.
- `documentationURL`: `https://github.com/Cleler/devcontainer-features/tree/main/src/<name>`; `licenseURL`:
  `https://github.com/Cleler/devcontainer-features/blob/main/LICENSE`.
- `dependsOn` for a hard dependency (reference `ghcr.io/Cleler/devcontainer-features/<id>:<major>`, e.g. `:1`).
  `installsAfter` is only a soft ordering hint among features the *consumer* selected, and it matches by exact id
  (a feature of another namespace is not matched): don't rely on it to order a feature of this repository.
- `mounts`: a bind-mount fails the whole container when the host source doesn't exist, and GitHub Codespaces doesn't
  support host bind-mounts. A Feature's own `initializeCommand` is ignored. If you need one, document the prerequisite
  in `NOTES.md` (see the `mkdir -p ~/.claude/devcontainer` of `claude`), or prefer a Docker named volume.

### `install.sh`

```bash
#!/bin/bash
set -e

if [ "$(id -u)" -ne 0 ]; then
    echo 'Script must be run as root. Use sudo, su, or add "USER root" to your Dockerfile before running this script.'
    exit 1
fi
```

- Detect the package manager: `apt-get`, `dnf`/`microdnf`/`yum` and **`apk` (Alpine)**. On Alpine: `apk add --no-cache`,
  `addgroup`/`adduser` (BusyBox has no `groupadd`/`usermod`), GNU `grep` and `coreutils` are separate packages, no glibc.
- `bash` must be there (the `bash` shebang): Dev Containers base images have it, a bare `alpine` doesn't.
- Keep it idempotent and clean up after itself.

### `NOTES.md` and `README.md`

- Write the documentation in `NOTES.md` (usage, requirements, OS support, limits). Never edit `README.md`.
- Generate it, then restore the footer line the workflow writes (full GitHub URL instead of the relative link the local
  CLI writes):

```bash
devcontainer features generate-docs -p src -n Cleler/devcontainer-features
git checkout <READMEs you did not mean to change>
```

### `test/<name>/test.sh` — the autogenerated test

Runs on **every image of the CI matrix** (Ubuntu, Debian, Alpine, bare images), as root, with the default options. It
only checks what is true on all of them, in the style of `test/claude/test.sh`:

```bash
#!/bin/bash

set -e

source dev-container-features-test-lib

check "<what>" <command>

reportResults
```

What is specific to a distribution, a user or an option goes in a **scenario**: `test/<name>/scenarios.json`

```json
{
    "alpine": {
        "image": "mcr.microsoft.com/devcontainers/base:alpine",
        "features": { "<name>": {} }
    }
}
```

and `test/<name>/alpine.sh` (same `check`/`reportResults` shape). Rules learned the hard way:

- A scenario **can't bring its own files** (no `Dockerfile` next to the JSON): use an `image`.
- A feature id **without `/`** is a local feature of `src/`; anything else must be a registry reference
  (`ghcr.io/devcontainers/features/common-utils:2`).
- A scenario that combines several features of this repository goes in `test/_global/` instead (named after its script).

## 3. Wire it into the repo

1. `.github/workflows/test-pr.yaml` → add a filter for `<name>` in the `detect-changes` job (copy an existing one: the
   `README.md` and `NOTES.md` negations are what skips the tests for a docs-only change).
2. `.github/workflows/test-all.yaml` → add `<name>` to the list of features (the default of the `features` input and
   the two fallbacks).
3. `.github/workflows/_test-autogenerated.yaml` → add an `exclude` for each image it can't run on (with a comment).
4. `README.md` (root: features section, table, dependency graph if it depends on another one) and the features table
   of `AGENTS.md`.
5. Nothing for the release: a feature whose version has no tag is published, and tagged, after the merge.

## Copy of an official feature (with Alpine support)

1. Copy `src/<id>` and `test/<id>` from the official repository (keep `scripts/` if `install.sh` sources them).
2. In `install.sh`, **only add**: an `alpine` case next to each `debian`/`rhel` one, an `apk` package manager branch.
   Don't remove or rewrite the official code, so the next upstream update stays a small diff.
3. In `devcontainer-feature.json`: our `documentationURL`/`licenseURL`, `"version": "1.0.0"`, a mention of Alpine in the
   description. Replace `installsAfter` on the official feature by a `dependsOn` on our `node` when it needs Node.js.
4. In `NOTES.md`: the Alpine specifics in the OS support section, and a final `## Source` section linking the official
   folder (`https://github.com/<owner>/<repo>/tree/main/src/<id>`).
5. Tests: keep the official `test.sh` or a clearer one, add `alpine*` scenarios on `mcr.microsoft.com/devcontainers/base:alpine`
   (and `alpine-3.22` for the previous version). Replace a local `common-utils` of the official repository by
   `ghcr.io/devcontainers/features/common-utils:2`.
6. Add it to the upstream-sync item of `TODO.md` if it isn't there.

## 4. Verify

```bash
jq empty src/<name>/devcontainer-feature.json
bash -n src/<name>/install.sh
shellcheck -S error src/<name>/install.sh        # if available; this is what the CI runs
devcontainer features test -f <name> .
```

`devcontainer features test -f <name> --skip-scenarios -i mcr.microsoft.com/devcontainers/base:alpine .` runs the
autogenerated test on one image. `claude` and the plugin need `mkdir -p ~/.claude/devcontainer` first.

## 5. Commit and PR

Only if explicitly asked to commit *this turn*. Work on a branch, push, open a PR to `main`, then enable auto-merge
(`gh pr merge --auto --merge`): the ruleset of `main` requires `shellchecker`, `validate` and the `check` jobs of the
test workflows. The Automated Maintenance workflow then does the rest (README, version, tag) after the merge.
