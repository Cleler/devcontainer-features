# AGENTS.md — devcontainer-features

## This Repository

**Purpose:** a registry of Dev Container Features, published to `ghcr.io/cleler/devcontainer-features/<id>`. The
features are independent of each other; when one needs another it declares it with `dependsOn` (see the table).

```text
src/<feature>/
├── devcontainer-feature.json  # id, version, options, dependsOn, mounts, containerEnv, customizations
├── install.sh                 # runs as root at build time
├── NOTES.md                   # the hand-written part of the README
└── README.md                  # GENERATED from devcontainer-feature.json + NOTES.md: never edit it by hand
test/<feature>/
├── test.sh                    # "autogenerated" test: one run per image of the CI matrix
├── scenarios.json             # optional: named scenarios (own image + options)
└── <scenario>.sh              # one script per scenario, named after its key in scenarios.json
test/_global/                  # scenarios that combine several features (scenarios.json + one script each)
```

**Features:**

| Feature | Depends on | Description |
| ------- | ---------- | ----------- |
| `node` | — | Node.js via nvm, yarn, pnpm |
| `claude-code` | `node` | Claude Code CLI |
| `claude` | `claude-code` | Claude Code (CLI + VS Code extension), configuration shared between all devcontainers |
| `claude-plugin-devcontainer` | `claude` | Claude Code plugin with skills and agents for working in a devcontainer |

**A `dependsOn` is resolved from the published registry, never from `src/`** (see "Testing"): a dependency has to be
released before what depends on it.

**A feature adapted from an existing one** keeps the original code, adds to it instead of rewriting it, and ends its
`NOTES.md` with a `## Source` section linking the original folder. Nothing keeps these up to date yet: see `TODO.md`.

**install.sh:** `bash` shebang · root check · package manager detection (`apt`, `dnf`/`yum`/`microdnf`, `apk`) · idempotent.

## Testing

```bash
devcontainer features test -f <feature> .                                       # autogenerated tests and scenarios
devcontainer features test -f <feature> --skip-scenarios -i <image> .           # the autogenerated test on one image
devcontainer features test -f <feature> --skip-autogenerated --filter <scenario> .   # one scenario
devcontainer features test --global-scenarios-only .                            # the global scenarios
```

- `test.sh` runs on every image of the CI matrix: it only checks what is true on all of them. What is specific to a
  distribution, a user or an option goes in a **scenario** (`scenarios.json` + `<name>.sh`).
- A feature with a host prerequisite (a mount source) documents it in its README: create it before testing.
- **A scenario can't bring its own files** (a `Dockerfile` next to `scenarios.json` isn't found: the CLI only copies
  `src/<feature>` into the test workspace). Use an `image`.
- **In a scenario, a feature id without `/` is a local feature (`src/<id>`).** A feature that is not in this repository
  must be a registry reference (`ghcr.io/devcontainers/features/common-utils:2`, not `common-utils`).
- **`dependsOn` is resolved from the published registry**, not from `src/`: only the feature under test is built from the
  working tree. A change that needs an unreleased dependency fails until the dependency is released: release it in its
  own PR first.
- Global scenarios (`test/_global/`) are named after their script, and only run when a feature they use changed.

## Versions, publication and tags

**Versions are incremented automatically**: don't bump a version for an ordinary change. The
[Automated Maintenance](.github/workflows/automated-maintenance.yaml) workflow, after each push on `main`, compares each
feature with the git tag of its current version (`feature_<id>_<version>`):

- `src/<id>/` changed since that tag (`README.md` and `NOTES.md` excluded) → patch + 1 (`.github/scripts/maintenance/plan.sh`),
  and a line (the subjects of the commits) at the top of the **Changelog table of its `NOTES.md`** (`changelog.py`);
- the README does not match what `NOTES.md` + `devcontainer-feature.json` generate → regenerated, after the previous step
  (`generate-docs` comes after `update-version`), so the changelog line reaches the README;
- all of it goes in **one PR** `automated-maintenance-<date>`, created by the GitHub App, merged automatically when its checks
  pass. Its `release / check` publishes the new versions (OCI packages on GHCR) and pushes one annotated tag per
  feature, whose message says what changed (`Release <id> <version> (<old> -> <new>)`, the commits, `Documentation: updated`);
- a feature whose current version has **no tag** (a new feature, a version you incremented yourself) is published
  directly after the push.

**Increment the version yourself only for a bigger change** (minor, major): put the new version in
`devcontainer-feature.json`, the maintenance then just publishes it. A new feature starts at `1.0.0`.

**No GitHub releases, only tags**, as in `devcontainers/features`. Nothing under `test/` or `.github/` ever needs a
version: they are invisible to a consumer of the feature.

## CI

Workflows are in `.github/workflows/` (GitHub doesn't read subfolders; the reusable ones are prefixed with `_`):

| Workflow | When | What |
| -------- | ---- | ---- |
| `lint-and-validate.yaml` | PR, manual | `shellchecker` (shellcheck, severity error, `src/**/*.sh`) and `validate` (schema of the `devcontainer-feature.json`). If one fails, `cancel-others` cancels the other runs of the commit |
| `test-pr.yaml` | PR | `detect-changes` (paths-filter, README/NOTES ignored) then `test-autogenerated`, `test-scenarios`, `test-global`, each one a call to `_test-*.yaml` |
| `release-pr.yaml` | PR | calls `_publish.yaml`: publishes only on the `automated-maintenance-*` PRs; the `release / check` exists on every PR |
| `test-all.yaml` | weekly (Monday), manual | the same three blocks on every feature (catches what comes from outside: new base images, new upstream versions) |
| `automated-maintenance.yaml` | push on `main`, manual | see "Versions, publication and tags" |
| `cleanup-maintenance-branches.yaml` | daily, manual | deletes the `automated-maintenance-*` branches without open PR |
| `linter-manual.yaml` | manual | shellcheck on a chosen path and severity |

- Each `_test-*.yaml` ends with a `check` job (`if: always()`), successful only if all its other jobs are (or if there
  was nothing to run). The ruleset of `main` requires these fixed names: `shellchecker`, `validate`,
  `test-autogenerated / check`, `test-scenarios / check`, `test-global / check`, `release / check`. A job-level `if`
  on the calling job would make the check disappear (a required check that doesn't exist blocks the PR): skip the
  work *inside* the called workflow.
- **A PR created with `GITHUB_TOKEN` triggers no workflow** (no checks, no release, so no auto-merge): the maintenance
  uses the token of a GitHub App (`APP_ID`, `APP_PRIVATE_KEY`; *Contents* and *Pull requests* write). The repository
  needs *Allow auto-merge*.
- The maintenance publishes **before** the merge (from the PR branch: the tag is on the PR head commit); a PR that is
  closed without merging leaves its version published.
- The tests of a feature don't run for a change of its `README.md`/`NOTES.md` only: `detect-changes` skips them.

## Adding a new feature — checklist

1. `src/<name>/devcontainer-feature.json` + `install.sh` + `NOTES.md` (then generate the README: see below).
2. `test/<name>/test.sh` (+ `scenarios.json` and scripts for what is specific to a distribution or an option).
3. `.github/workflows/test-pr.yaml` → add a filter for the feature in `detect-changes`; `.github/workflows/test-all.yaml`
   → add it to the list of features (the default of the input and the two fallbacks).
4. `.github/workflows/_test-autogenerated.yaml` → `exclude` the images it can't run on.
5. `README.md` (root: features, table, dependency graph) and the table above in this file.
6. A global scenario in `test/_global/` if it works together with another feature.
7. Nothing to do for the release: a version without tag is published after the merge.

**README generation** (the feature README is never edited by hand; `NOTES.md` is):

```bash
devcontainer features generate-docs -p src -n Cleler/devcontainer-features
```

The local CLI writes the last line (`auto-generated from the devcontainer-feature.json`) with a relative link; the
workflow writes it with the full GitHub URL: restore the URL form before committing, as the files in `main` have it.

## Conventions

- **`NOTES.md`** is the hand-written part of the README. Skeleton, to keep the sections that apply: `Requirements`,
  `How it works`, `Supported distributions`, `Changelog`, then `Source` for a feature adapted from another one. The
  `Changelog` is a table (`| Version | Notes |`, newest first) that the maintenance fills for each new version; write
  the first line (`1.0.0 | Initial version`) yourself, and the line of a minor/major version you bump yourself.

- **`devcontainer-feature.json` must be plain JSON** (no `//` comments), keys in this order: `name`, `id`, `version`,
  `description`, `documentationURL`, `licenseURL`, `options`, then the rest (a feature adapted from another one keeps
  the order of the original file).
- **A `mounts` entry fails the whole container if the host source doesn't exist**, and a Feature's own
  `initializeCommand` is ignored: document the prerequisite in the feature's `NOTES.md` instead (or use a named
  volume). GitHub Codespaces doesn't support host bind-mounts at all.
- **Git:** work on a branch, open a PR to `main`, enable auto-merge (`gh pr merge --auto --merge`): the ruleset
  decides. Merge commits, no squash. Commit only when asked.
- **Tests that must fail** (to check that a check turns red) go in a PR that is closed without merging, never on `main`.
- **License:** MIT, no header in the files.
